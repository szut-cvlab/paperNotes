### REINFORCED & ADVANCED VISUAL REASONING

> 官方定位：Models that think, reason, and understand the visual world at a granular level.

#### VLM-R1（6k★，组织门面）

- **Github地址**: https://github.com/om-ai-lab/VLM-R1
- **权重地址**: https://huggingface.co/omlab/VLM-R1-Qwen2.5VL-3B-OVD-0321（另有 [Math](https://huggingface.co/omlab/VLM-R1-Qwen2.5VL-3B-Math-0305)、[REC](https://huggingface.co/omlab/Qwen2.5VL-3B-VLM-R1-REC-500steps) 版本）
- **论文地址**: https://arxiv.org/abs/2504.07615（arXiv，未见会议发表信息）
- **定位**: R1 风格强化学习 VLM（"Solve Visual Understanding with Reinforced VLMs"），GRPO 训练
- **核心发现**: 同一基座（Qwen2.5-VL-3B）+ 同一份数据（RefCOCO 指代表达理解），SFT 与 GRPO 两种训法各训一遍。域内数据上 100~600 步两者分数接近；域外数据（LISA-Grounding 等训练时没见过的分布）上 SFT 训得越久成绩越差（过拟合训练分布），RL 稳步上升。一句话：SFT 学的是「这批数据的答案长什么样」，RL 学的是「怎么完成任务」。
- **贡献**: 不改模型架构（现成 Qwen2.5-VL / InternVL 直接做 RL 后训练），纯靠实验证明 GRPO 配方在 VLM 上成立且泛化更强。三件事：① 实证结论——回答了当时「视觉任务没有像数学题那样清晰的可验证奖励，RL 到底行不行」的疑问；② 奖励函数模板——趟出视觉任务怎么造奖励（IoU 类 + odLength/weighted_sum/cosine 变体）；③ 工程基建——jsonl 数据格式、多图输入、LoRA/多节点训练、自定义奖励接口，2025 年初最早一批能直接抄作业的 VLM RL 框架。也因此没有会议发表：recipe 型工作在传统审稿眼里创新性不足，但工程影响力大于很多中稿论文
- **基座**: Qwen2.5-VL-3B、InternVL；DeepSpeed ZeRO-3；支持 LoRA、多图、多节点、自定义奖励函数
- **任务**: REC（指代表达理解）/ OVD（开放词汇检测，OVDEval SOTA）/ Math（OpenCompass 4B 以下第一，2025-03）/ GUI 缺陷检测
- **工程化**: 已适配华为昇腾（Atlas 800T A2 / 300I Duo），2025-08 基于 JD xllm 优化 TTFT 降 50%、吞吐 +127%
- **时间线**: 2025-02 首发，最后更新 2025-08

#### vlm-r1seg（4★，实验性）

- **Github地址**: https://github.com/om-ai-lab/vlm-r1seg
- **权重地址**: 无统一权重页（best checkpoint 路径列在 README，如 `Seg-Zero_best_ckpt`）
- **论文地址**: 无（方法基于 Seg-Zero 框架的变体/复现）
- **定位**: VLM-R1 的推理分割分支——R1 式 RL 微调 Qwen2.5-VL-7B，SAM2（冻结）按 VLM 输出的框生成掩码
- **与 VLM-R1 的区别**: 架构和数据同源（训练数据同为 RefCOCOg 族描述式指令），只改训练配方——输出强制带 thinking 推理链、奖励加 SAM 掩码质量（bbox IoU 仍保留）、关掉 KL。ReasonSeg（推理式查询，零样本）是评测集不是训练集；配方一改，没训过的推理行为就逼出来了，等于把「RL 学的是能力不是数据分布」又验证了一格。一句话：VLM-R1 证明 RL 能出准框，这个实验问 RL 出的框能否连掩码也准
- **训练配方**（从 checkpoint 命名解码）: 输出走 thinking format（先推理再给框）+ seg format；奖励 = bbox IoU + mask trim + SAM 作奖励模型（rewardmodelsam）+ clip 权重调高（cliphiger）；**关闭 KL 散度惩罚**（nokl）
- **数据**: 训练用 refCOCOg_9k_840_mask（RefCOCOg 9k 图像子集转掩码格式，仓库 `codebase/dataset_tools/` 提供三段转换脚本）；HF 发布测试集 `Zilun/RefCOCOg_test`（5023 条）
- **成绩**: ReasonSeg GIoU 0.6113 / cIoU 0.5497；RefCOCOg-test GIoU 0.7440 / cIoU 0.7392
- **完成度**: 代码是全的——数据制作 5 个脚本在 `codebase/dataset_tools/`（RefCOCOg 训练/验证测试集转换、掩码格式制作），RL 训练整套在 `codebase/Seg-Zero/`（verl 框架的 GRPO 核心 + 训练脚本 + model_merger + 推理脚本 + Dockerfile，IoU/L1/format/accuracy 奖励已实现）；脏的是硬编码本地路径（`/training/zilun/...`）、wandb 手动同步、无 description/topics/releases、无许可证。；vlm-r1seg 特有的奖励改动（rewardmodelsam、cliphiger）落在哪个文件需进 `verl/` 翻 reward 源码

#### ZoomEye（98★）

- **Github地址**: https://github.com/om-ai-lab/ZoomEye
- **权重地址**: 无（不训新模型，直接加载 LLaVA/InternVL2.5/Qwen2.5-VL 等基座 checkpoint）
- **论文地址**: https://arxiv.org/abs/2411.16044（**EMNLP 2025 Oral，CCF-A**）
- **定位**: 给 MLLM 加「类人缩放」。痛点：MLLM 推理时视觉输入固定（整图一次塞入，token 分辨率有限，小目标细节直接丢了），推理只发生在文本层；ZoomEye 把推理搬到视觉层——免训练、模型无关，纯靠推理时树搜索
- **机制**:
  - **树表示**：根节点 = 整图，每个子节点 = 父节点四等分（2×2 不重叠，可配 9/16 宫格），递归划分直到满足图像编码器分辨率
  - **打分引导（best-first）**: 用 MLLM 的 Yes/No next-token 概率给每个候选块打两种置信度——existing（这块里有没有目标）和 latent（再放大能不能找到），按深度加权排序（浅层偏 latent、深层偏 existing），优先队列决定下一个看哪块
  - **停止/回溯**: 问「现在能回答了吗」，回答置信度超阈值（0.8/0.6）就停；没找到就从优先队列弹下一块（天然回溯）；步数超限则逐步降低阈值兜底
  - **收尾**: 搜到的节点框取并集，把聚焦区域喂给模型出最终答案；搜索前先让 LLM 用 ICL 生成视觉线索（单实例/全部实例两类）驱动定向搜索
- **例子**: 问「图中的汽水罐是什么颜色」（罐子在 8K 图里只有几十像素）。第 0 步先让模型生成线索「汽水罐」；第 1 步整图切 2×2 四块，逐块问「这里有罐子吗」「放大这块能找到吗」，左下块 latent 分最高；第 2 步放大左下块再切四块，往分高处钻；第 3 步每个节点问「现在能回答了吗」，置信度过 0.8 就停；第 4 步发现找到的是红水桶？弹队列里下一个候选块接着找（回溯）；第 5 步命中罐子，框取并集聚焦输入 → 答「蓝色」
- **成绩**: InternVL2.5-8B 在 HR-Bench 4K/8K 上分别 +15.71% / +17.69%；让 3-8B 小模型在相关基准上超越 GPT-4o
- **支持模型**: LLaVA-v1.5、LLaVA-OneVision、InternVL2.5、Qwen2.5-VL：
  - LLaVA-v1.5：CLIP ViT-L 底座，任何图硬缩 336×336 固定分辨率——小目标绝症，缩放收益最大
  - LLaVA-OneVision：SigLIP 底座 + anyres 动态切片，保原始宽高比切多块，块数有上限
  - InternVL2.5：动态瓦片，448×448 一块。视觉编码器 InternViT-6B，每块独立编码：448÷14 = 32，即 32×32 = 1024 个 patch，2×2 合并后每块压成 256 个视觉 token；12 块 + 缩略图共 13×256 = 3328 token 进 LLM，「最多 12 块」本质是卡这个 token 预算。模板集 = 所有 i×j≤12 的整数网格（1×1、3×2、4×3、6×2、12×1 等，12 块的模板有 6 种：3×4/4×3/2×6/6×2/1×12/12×1），按**宽高比最接近**挑而非块数最多，另附缩略图。例：7680×4320 的 16:9 图最接近 2:1 → 只分到 2 块，整图缩到 896×448，80×80 的罐子只剩 9×5 像素——图越大不等于切得越多
  - Qwen2.5-VL：原生动态分辨率——ViT 按 14×14 像素一格切 patch，每个 14×14 patch 编码成一个 C 维 embedding，最后将相邻 2×2 的 4 个 embedding 沿**通道维度拼接**，再过一个 MLP 投影作为 1 个 token（相当于28×28）。上限：官方 qwen-vl-utils 默认 max_pixels = 16384 个 token ≈ 1284 万像素（可配置），超限整图等比降采样；实际部署/API 常配得更低（如 1280 token ≈ 100 万像素）。所以业内（Qwen、InternVL、LLaVA-Next 的 pixel shuffle）统一走「细 patch 编码 + 后压缩」
- **时间线**: 2024-11 发论文 → 2025-08 EMNLP 2025 Main Oral（CCF-A）→ 2025-11 放出 InternVL2.5/Qwen2.5-VL 版本代码；许可证未标注

#### ImageRAG（36★）

- **Github地址**: https://github.com/om-ai-lab/ImageRAG
- **权重地址**: https://huggingface.co/omlab/ImageRAG（含 checkpoint + cache + 数据集）
- **论文地址**: https://arxiv.org/abs/2411.07688（**IEEE GRSM 2025**，[DOI](https://doi.org/10.1109/MGRS.2025.3574742)）
- **定位**: RAG 增强超高分辨率（UHR，如 10000×10000）遥感影像分析。两难：整图缩小喂 → 小目标信息直接没了；按原尺寸喂 → 远超任何模型的 token 上限
- **核心思想**: 把 UHR 影像当「可检索的数据库」——离线把影像切 patch 提特征建向量库，查询时按文本问题检索相关 patch，只把命中的区域喂给 MLLM。三步：
  1. **离线建库**: 影像切 patch 提特征（编码器可选 CLIP/GeoRSCLIP/RemoteCLIP/MCIP-CLIP），入向量库；patch 数量大（一张图成百上千个），用 Ray（Python 分布式计算框架）把提特征任务并行分到多卡/多机跑，缩短建库时间
  2. **在线检索**: 用户问题 → 图文检索命中最相关 patch → 精选代理区域给 MLLM。三个设计维度单因素消融（默认 CLIP × Cascade Grid × Clustering）：编码器上**通用 CLIP 反超遥感微调版**（GeoRSCLIP/RemoteCLIP 更差，反直觉）；patch 划分三种（ViT/Cascade Grid/Complete Cover）平均分差距很小，ViT 最均衡；代理选择三法平均持平，因 Clustering 太耗时论文实用推荐 Prototype
  3. **聚焦推理**: 命中区域取并集 → 微调过的 InternVL2_5-8B 生成回答
- **双路检索**: 主影像 patch 库检索失败时走慢路——用问题关键词查两个**外部知识库**（与主影像库无关）：LRSD（7 个公开数据集裁出的 142 类带标签目标小图，约 160 万张）和 CRSD（RS5M 的 PUB11 子集，约 300 万图文对），拿到该概念的「视觉原型」embedding 后回主影像做图-图检索。人话版：「机场」直接搜不动时，先去知识库看机场长什么样，再拿长相回主图找
- **训练**: LoRA（alpha 32）微调 InternVL2_5-8B，数据 1.4 万条自建集——Zoom4K（约 4000 条定位，11 类方位词）+ VQA10K（1 万条，STAR/FIT 的 512×512 子块问答）；8×A100 训 2 epoch 仅 2 小时。效果：无线索时不伤原能力（46.67 持平），给 ROI 线索 60.00，配 CoT 64.67（MME-RealWorld-Lite-RS）
- **贡献**: ① 把 RAG 从「检索文本文档」搬到「检索影像区域」，同时绕开「缩放丢细节」和「原图超 token」两个死结；② 检索 + 轻量 LoRA，不用为高分辨率重训大模型，也不需要密集标注；③ 知识库可外挂扩展（CRSD/LRSD），新数据进库即可用
- **评测**: MME-RealWorld-RS（VQA），README 未列具体分数，结果见仓库 `imagerag_result` 目录
- **备注**: 依赖较重（SGLang 部署 Qwen2.5-32B 做文本解析）；MIT；作者 TODO 自述代码未在隔离环境验证过

### REAL-TIME PERCEPTION & OPEN-WORLD VISUAL DETECTION（实时感知与开放世界检测）

> 官方定位：Foundational spatial understanding optimized for edge and on-premise speeds.

#### OmDet（1.4k★）

- **Github地址**: https://github.com/om-ai-lab/OmDet
- **权重地址**: https://huggingface.co/omlab/omdet-turbo-swin-tiny-hf（已集成进 Transformers v4.45.0，另有 ModelScope）
- **论文地址**: https://arxiv.org/abs/2403.06892（arXiv，未见会议发表信息）
- **定位**: 实时开放词汇端到端检测；本仓库是 OmDet-Turbo 官方 PyTorch 实现。把 DETR 类检测器 + 语言模态做开放词汇检测（OVD），但把推理压到实时档（A100 上 Base 100+ FPS）。前作 OmDet 与同期 Grounding-DINO 在 OVDEval 上都很强，但都太慢——这篇就是冲着「又快又开放词汇」去的
- **核心思想**: 在 OmDet / Grounding-DINO 基础上做减法，两个关键改动：
  1. **Efficient Fusion Head（EFH，高效融合头）**: 先前模型（尤其 Grounding-DINO）把文本特征塞进解码器每一层的 cross-attention，文本一多计算量爆炸。EFH 把「文本-图像多模态融合」用轻量头一次性完成，不再逐层融，从而减轻编码器与 ROI 检测头开销
  2. **Language Cache（语言缓存）**: OVD 落地时类别词表往往是固定的（一个部署里就那么几十类）。Turbo 把这套固定词表的文本 embedding 离线算一次缓存下来，推理时文本编码器不再每帧跑，每帧只过图像——「Turbo」之名即来自此；配合 TensorRT 后 Base 跑到 100.2 FPS
  3. **三任务统一**: 延续前作 OmDet 的统一架构，同一套模型覆盖 Grounding（短语定位）、OVD（开放词汇检测）、Referring Detection（指代检测）
- **训练**: 大规模视觉-语言多数据集预训练——Tiny 明确用 **Objects365（O365）+ GoldG**（GoldG = LVIS/Flickr/Visual Genome/GQA 等合并）；另含 COCO、RefCOCO/RefCOCO+/RefCOCOg 等。骨干可选 Swin-Tiny / Swin-Base。零样本设定，不靠目标域标注
- **成绩**: Turbo-Tiny 零样本 COCO 42.5 / LVIS 30.3，FPS 21.5（PyTorch）/ 140（TensorRT）；Turbo-Base ODinW AP 30.1、OVDEval NMS-AP 26.86（当时零样本 SOTA），A100 上 100.2 FPS；COCO/LVIS 零样本接近同档有监督 SOTA
- **贡献**: ① 首个把 DETR 类 OVD 检测器压到实时档（100+ FPS）的工作，靠 EFH + Language Cache 而非堆算力；② 在 ODinW / OVDEval 上刷新零样本 SOTA，且 COCO/LVIS 零样本逼近有监督模型；③ 三任务（Grounding/OVD/Referring）统一架构，已进 Transformers v4.45、可转 ONNX、能当 OmAget 多模态 agent 的 OVD 工具
- **评测**: 零样本基准 COCO、LVIS、ODinW、OVDEval；速度在 COCO val2017 上测
- **备注**: Apache-2.0；论文另见 IET Computer Vision 2024（作者 Tiancheng Zhao 等，ByteDance/OM-AI-Lab）；已集成进 HuggingFace Transformers v4.45.0，ModelScope 也有；支持 ONNX 导出与本地/API（run_wsgi.py）部署

#### VLM-FO1（334★）

- **Github地址**: https://github.com/om-ai-lab/VLM-FO1
- **权重地址**: https://huggingface.co/omlab/VLM-FO1_Qwen2.5-VL-3B-v01（另有 ModelScope）
- **论文地址**: https://arxiv.org/abs/2509.25916（arXiv 2025-09，未见会议发表信息；题名 *Bridging the Gap Between High-Level Reasoning and Fine-Grained Perception in VLMs*）

  1. **Hybrid Fine-grained Region Encoder（HFRE，双视觉编码器）**: 一路出语义丰富的特征、一路出感知增强（空间细节）特征，融合成强大的 **region token**，同时带高层语义与细粒度空间信息

- **贡献**: ① 首个即插即用、冻结基座就能给任意 VLM 补细粒度感知且不掉通用能力的方案；② 双视觉编码器 region token + token 引用机制，把坐标生成问题转成特征检索，更稳；③ 可外接 UPN（ChatRex）/SAM3 等检测器，覆盖 grounding、区域理解、计数甚至视频跟踪（SAM3 + VLM-FO1 demo）

### MULTIMODAL AGENTS & EMBODIED AI（多模态智能体与具身 AI）

#### OmAgent（2.7k★）

- **Github地址**: https://github.com/om-ai-lab/OmAgent
- **权重地址**: 无（框架项目，模型走 API 或本地部署 Ollama/LocalAI）
- **论文地址**: https://arxiv.org/abs/2406.16620（**EMNLP 2024，CCF-A**）
- **定位**: 多模态语言智能体框架，快速原型 + 生产两用；`pip install omagent-core`（论文 *OmAgent: A Multi-modal Agent Framework for Complex Video Understanding with Task Divide-and-Conquer*，EMNLP 2024，CCF-A）
- **核心思想**:
  1. **Divide-and-Conquer Loop（分而治之推理环）**: 把长视频问答拆子任务，逐子任务去检索相关内容再拼答案。检索计划（查哪段、是否继续）在 video_understanding 示例里由 **DnC 任务树结构性决定**（分解→每子任务查 Milvus→汇总），而非 ReAct 环动态驱动——但广义上 ReAct 的 action 步本可把检索当工具调用
  2. **图编排引擎**: 智能体由可复用「agent operator」（CoT/ReAct/SC-CoT 等现成推理算子）像搭积木拼成有向图，节点/边依赖用 `container.yaml`（由 `compile_container.py` 生成）配置，不用手写调度
  3. **记忆抽象 + 推理算子**: Redis 做短期记忆/状态，Milvus 做长期记忆（向量库）；CoT/ReAct/SC-CoT/ReAct-Pro/POT 是**可插拔的推理/行动范式**（在 gsm8k/AQuA 上做基准对比），用来「规范某一步怎么思考 / 是否调工具」。它们是通用脚手架，不专属视频检索：现代 VLM 已自带隐式 CoT，裸 CoT 算子必要性下降，但 ReAct 的**工具调用闭环**与 SC-CoT 的**自洽投票**仍是基座模型不会自发的系统级能力
- **例子**: 「嫌疑犯进楼时穿什么？」→ DnC 拆子问题 → 检索相关片段摘要 → VLM 作答
- **实现真相（与论文叙事的落差，`video_preprocess.py` 源码确认）**:
  - **预处理是离线批量，非实时流式**: 先读整个视频算 MD5、抽全部音频、遍历所有镜头、结果 pickle 落盘缓存——必须拿到完整视频跑一遍 preprocess 才能问答。论文「24h 监控实时理解」是愿景，实现是离线
  - **缓存的是文字，不是帧**: 场景检测用 PySceneDetect `ContentDetector`（逐帧像素平均绝对差超阈值 27 判镜头切换——是**像素突变检测，非语义场景**，对无剪辑的监控摄像头不友好）→ 每 scene 抽帧，并取该场景 **STT（语音转文字）结果**，帧图 + STT 文本一并喂 `gpt4o` 出详细文字摘要 → `text-embedding-3-large`（3072 维）编码 → 存 Milvus。检索比对的是**文字向量**，论文吹的「保住视觉细节 / 帧不丢」在这份开源代码里**并未兑现**（恰恰是自己批评过的「转文字」做法）
  - **每视频一套索引**: 摘要向量按视频 md5 打标存进 Milvus，相当于每个视频建一套可检索索引
- **贡献**: 论文科学贡献是**长视频「分而治之 + 按需检索」范式**让 24h 监控/整部电影这类标准 VLM 搞不定的任务可行；图编排/记忆/推理算子是其工程框架外壳。但需注明：开源 video_understanding 示例实际落地为「场景文字摘要 → 向量检索」，与论文「存帧保细节」的叙事有落差
- **能力**: 原生多模态（文本/图/视频/音频），通用能力含 VLM、实时 API、CV 模型、移动端连接（移动助手为仓库 README 自带 demo，非论文评测）
- **部署**: 完全分布式架构可自定义扩缩容；**Lite 模式免中间件**——分布式模式靠 worker 编排 + 任务队列（消息中间件）在多处调度节点，Lite 模式全进程内跑，单机原型不必部署 broker
- **备注**: OmAgent 是**通用智能体框架**，视频理解只是论文旗舰 demo；`open-agent-leaderboard` 复用其 AGORA 图编排引擎做数学 agent 基准，是同一引擎的不同应用（见下方「智能体线」）

#### open-agent-leaderboard（36★）

- **Github地址**: https://github.com/om-ai-lab/open-agent-leaderboard
- **权重地址**: 无（排行榜项目）
- **论文地址**: https://aclanthology.org/2025.acl-demo.11/（**ACL 2025 System Demonstrations，CCF-A**）
- **定位**: 可复现的语言智能体算法排行榜（论文 *Unifying Language Agent Algorithms with Graph-based Orchestration Engine for Reproducible Agent Research*），**复用 OmAgent 的 AGORA 图编排引擎作为底层基础设施**（而非其视频能力），把 CoT/ReAct 这些「推理范式」做成统一可换组件，在**数学推理数据集**（agent 算法的标准评测域，非视频任务）上横向对比
- **评测**: 3 数据集 × 算法（IO/CoT/SC-CoT/PoT/ReAct-Pro/ToT）× 11 LLM（gpt-3.5-turbo、gpt-4o、Qwen2.5-72B/7B、Llama-3.3-70B、deepseek-r1 等；本地部署的开源模型成本计 $0）
- **数据集（三个全是数学推理，难度递增）**:
  - **gsm8k**: 小学数学应用题，考多步算术推理（8-shot，评测 1319 题）
  - **AQuA**: 代数选择题，带干扰项（0-shot，254 题）
  - **MATH-500**: 竞赛数学 MATH 的 500 题子集（代数/几何/数论），难度最高（4-shot）
- **算法基本原理**:
  1. **IO（Input-Output）**: 直接问直接答，无中间推理步骤——基线参照
  2. **CoT（Chain-of-Thought）**: 提示模型先一步步推理再给最终答案
  3. **SC-CoT（Self-Consistency CoT）**: 温度 1 采样多条 CoT 链（path_num=5）再投票聚合，更稳但更贵
  4. **PoT（Program-of-Thoughts）**: 计算与推理解耦——模型写代码，执行代码得数值答案，算术题强
  5. **ReAct-Pro**: Thought（推理）与 Action（工具调用）交错迭代；按 Reflexion 仓库改造（max_steps=10），同 LLM 下比原版 ReAct 翻倍（gpt-3.5-turbo：gsm8k 74.91 vs 38.13，AQuA 64.57 vs 34.25），但 token 是 CoT 的 10–40 倍
  6. **ToT（Tree of Thoughts）**: 推理做成树搜索（bfs、max_depth=6、评估=投票），可分支回溯，最贵也最不稳
- **AGORA 引擎**: DAG 工作流——节点=任务（自定义逻辑或内置分支/循环控制流），基于 Netflix Conductor，支持可视化追踪调试 + 异步分布式执行
- **结论**: ① **SC-CoT + Qwen2.5-72B 第一**（平均 86.67：gsm8k 94.77 / AQuA 85.43 / MATH-500 79.8，总成本 $4.045）；② **CoT + Qwen2.5-72B 紧随其后（86.43）只要 ~$1.15，性价比之王**——论文核心发现：简单方法（CoT）往往以更低开销达到接近的鲁棒性能；③ **模型大小 > 算法**：大模型霸榜，Qwen2-0.5B/1.5B 用啥算法都垫底；④ **ToT 成本爆炸**：gpt-4o 上 gsm8k 花 $86.86、MATH-500 花 $40.81 却只拿 3.2 分；⑤ PoT 在 gsm8k 强（gpt-4o 93.10）但 MATH-500 弱；⑥ 可复现性验证过：与原 agent 仓库分数对齐（CoT gsm8k 78.70 vs 原版 79.23）
- **备注**: MIT；HF Space 在线排行榜；指标记录 score / pass rate（有效输出占比）/ token 数 / 成本（按公开定价折算）

- **构成**: Pub11（11 个公开图文数据集过滤清洗后约 300 万对）+ RS3（FMoW/BigEarthNet/MillionAID 共约 206 万，**均来自公开遥感基准**，原仅类别标签，由**预训练 VLM 生成描述**做成图文配对）；附 GeoMeta 地理元数据
- **成果**: 微调 CLIP 得 GeoRSCLIP，零样本分类 +3%~20%、遥感跨模态检索 +3%~6%、语义定位 +4%~5%；RSICD 检索 mR 38.87%（CLIP 基线 15.74%）
- **备注**: MIT；WebDataset = 把图像+文本打成 tar 分片便于流式读取（128 个分片 = train/val × {pub11,rs3} × 32，官方要求**勿解压**、用 dataloader 直读），吞吐约 1800 图/秒

#### OVDEval（63★）

- **Github地址**: https://github.com/om-ai-lab/OVDEval
- **数据集地址**: https://huggingface.co/datasets/omlab/OVDEval
- **权重地址**: 无（基准项目）
- **论文地址**: https://arxiv.org/abs/2308.13177（**AAAI 2024，CCF-A**）
- **定位**: **开放词汇检测（OVD）模型的评测基准**——OVD 指模型能检测「文字描述的任意物体」（不限于训练时的固定类别）。现有 OVD benchmark 只测「能否认出新类别」「能否按短语定位」，OVDEval 认为这不够、测不出模型是否真懂图文，于是加了 9 个细分理解任务 + 难负样本来逼出模型真实能力
- **9 个子任务（按标注文件，含实例）**: ① **negation** 否定/细粒度反例（"computer without screen on" vs "with screen on"）；② **color** / ③ **material** 属性（颜色、材质）；④ **position** 空间位置（"左边的杯子"）；⑤ **relationship** 物体关系（"猫旁边的狗"）；⑥ **celebrity** / ⑦ **landmark** / ⑧ **logo** 常识与知识（名人脸、地标、商标）；⑨ 论文统称「常识知识」等共 9 类。**注：这 9 类是「能力维度的抽样」而非穷举——尤其「常识/知识」桶是开放的，名人/地标/商标只是代表，理论上可无限加动物物种、品牌等；各维度边界也偏 ad hoc，是基准的设计弱点（任务覆盖启发式、非系统）**
- **难负样本 / 防表面匹配**: 每张图除正例 `text` 外还带 `neg_text`（同图细粒度反例），模型**必须不在反例上误触发**；只会「浅层关键词/纹理匹配」的模型会在这栽跟头
- **方法论贡献（NMS-AP）**: 发现**细粒度标签数据集上传统 AP 会虚高**——模型刷出大量重叠/近似框，原始 AP 计数放水。提出 **NMS-AP**：算 AP 前先做**非极大值抑制（NMS）**去掉冗余重叠框，得分才真实；该基准强制用 NMS-AP。例：GLIP 在 material 子集上 NMS-AP 仅 0.074，暴露现有 OVD 模型在这些细粒度任务上其实很弱
- **备注**: Apache-2.0；评测脚本 `eval.py`（`eval_glip.py` 给 GLIP 示例）；数据走 HF（omlab/OVDEval）

#### VL-CheckList（138★）

- **Github地址**: https://github.com/om-ai-lab/VL-CheckList
- **权重地址**: 无（示例模型权重在仓库 resources/ 目录）
- **论文地址**: https://arxiv.org/abs/2207.00221（**EMNLP 2022 System Demonstrations，CCF-A**）
- **定位**: **VLP（视觉-语言预训练）模型的可解释评测框架**——传统评测只给一个总分（如 VQA 准确率），混在一起看不出模型到底哪强哪弱；VL-CheckList 借鉴 NLP 的 CheckList 思路，把图文能力**拆成三类独立维度分别打分**：① **Object** 认物体（图-文里有没有某实体）；② **Attribute** 认属性（颜色/材质，如「黄色的狗」，用 Visual Genome + VAW 数据集）；③ **Relation** 认关系（空间/动作，如「狗在左边」「狗追猫」，改 object/attribute/大小/位置反复测）。输出**每个模型的三维分数表格 + 雷达图**，一眼看出短板（如某模型认物体强但认关系弱）
- **支持模型**: ViLT、ALBEF、TCL、UNITER、OSCAR、LXMERT、CLIP；`pip install vl_checklist`
- **备注**: 许可证未标注；HF Space 在线 demo；2022 年后基本停更

#### TRACE-BENCH（10★）

- **Github地址**: https://github.com/om-ai-lab/TRACE-BENCH
- **权重地址**: 无（基准项目，源视频需从 StreamingBench / OVO-Bench 上游下载）
- **论文地址**: https://arxiv.org/abs/2609.30670（arXiv，未见会议发表信息）
- **定位**: 本地可复现的流式视频理解基准（Temporal Audit and Condition-aware Evaluation），带时间戳的视频 QA + 主动响应（Proactive Response）双任务
- **构成**: v1.1.0 标准 833 QA + 407 Proactive（517 视频）；统一流协议（1 FPS 确定性帧采样 → Adapter 接口 → 可审计打分）
- **卖点**: 条件感知报告——质量、延迟、误报/漏报、工作量同框呈现（例：两款模型 QA 准确率相近但延迟差异巨大；MiniCPM-O 93.52% 无效输出率被直接暴露）
- **备注**: 代码 MIT，数据条款复杂（OVO-Bench 标注条款未解决）；与 VLX-Flow 同属流式视频理解布局

#### Probing-VLM-VGM（15★）

- **Github地址**: https://github.com/om-ai-lab/Probing-VLM-VGM
- **权重地址**: https://huggingface.co/SZhanZ/Probing-VLM-VGM（仅探测头权重，不含骨干）

#### OmChat（17★）

- **Github地址**: https://github.com/om-ai-lab/OmChat
- **权重地址**: https://huggingface.co/omlab/omchat-v2.0-13B-single-beta_hf（仅单图）
- **论文地址**: https://arxiv.org/abs/2407.04923（arXiv，未见会议发表信息）
- **定位**: **开源多模态大模型（MLLM/VLM）家族**——和 LLaVA/InternVL 同类，但专门强化**长上下文（最高 512K tokens）**与**视频理解**。做法：① **统一视觉处理 + 动态编码**（任意分辨率/长宽比图像，不切块网格）；② **统一提示策略**把单图/多图/视频塞进同一套 prompt，不分头模型；③ **渐进式多模态预训练**（active progressive pretraining）逐步把上下文窗口撑到 512K，而非从头硬训长上下文；④ 数据为中心（精选高质量数据 + 高质量 SFT）。还自提 **Temporal Visual Needle-in-a-Haystack** 基准，测长视频里「找特定瞬间」的时序理解。能力：单图 VQA 持平主流；多图推理 OmChat2.1-8B 在 Mantis-Eval 8B 档第一（67.28 超 GPT-4V 62.67）；视频 MMBench-Video 8B 档 SOTA（1.34，仅次于 GPT-4o 1.62 / GPT-4V 1.53）
- **构成**: OmChat2.0-13B = Qwen2-7B（LLM）+ InternViT-6B（视觉塔），基于 LLaVA/InternVL2 等代码；**注意 13B 权重目前只支持单图**，多图/视频靠 2.1-8B；Apache-2.0；2024 年底后基本停更


## 技术谱系与时间线

```
2021-2022  早期学术积累：VL-CheckList（EMNLP 22，CCF-A）、bottom-up-attention 复现
2023-2024  遥感线：RS5M/GeoRSCLIP（TGRS 24）→ ImageRAG（GRSM 25）
2024       检测线：OVDEval（AAAI 24，CCF-A）→ OmDet/OmDet-Turbo → GroundVLP（AAAI 24，CCF-A）
2024       智能体线：OmChat → OmAgent（EMNLP 24，CCF-A）→ open-agent-leaderboard（ACL 25，CCF-A）
2025       RL 线：VLM-R1（arXiv 2504）→ ZoomEye（EMNLP 25 Oral）→ vlm-r1seg
2025       感知线：VLM-FO1（arXiv 2509）→ 具身线：OmTrackVLA → VLX-Go
2026       VLX 旗舰系列成型：VLX-Seek（细粒度感知）→ VLX-VR（视频推理）→ VLX-Flow（流式）
           配套：TRACE-BENCH（流式评测）、Probing-VLM-VGM（空间智能探测）
```

**脉络总结**: 组织打法是「基准开路 → 模型跟进 → 旗舰整合」——先发评测基准（OVDEval、VL-CheckList、TRACE-BENCH）建立话语权，再出对应模型（OmDet 对 OVDEval、VLX-Flow 对 TRACE-BENCH），最终收拢到 VLX 旗舰系列，覆盖感知（Seek）、行动（Go/TrackVLA）、推理（VR/Flow）的 embodied 全链路。强化学习（VLM-R1/ZoomEye）是贯穿的方法论底座。

## 公开观察

- **开源策略分层**: 明星项目（VLM-R1、VLX-Seek）全量开源权重 + 训练代码；新旗舰（VLX-Flow/VR）先放论文和 API/SDK，权重滞后或不开源——关注后续 checkpoints 动态
- **活跃度断层**: 2026 年重心明显在 VLX 系列与具身方向；遥感线（RS5M/ImageRAG/awesome-RSVLM）和 OmChat/OmModel 已实质停更
- **许可证风险点**: VLM-FO1、OmTrackVLA、ZoomEye、vlm-r1seg、VL-CheckList 未见许可证标注，商用前需逐一确认
